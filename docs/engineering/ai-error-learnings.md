# AI 错误长期经验

本文件只记录高频、稳定或破坏性高，且值得长期防复发的错误模式。每条经验使用三行：`标题`、`来源`、`教训`，并与流水中的 `HE-FL-XXX` 关联。

## HE-FL-001 Skill 脚本用相对层级常数推断跨目录根路径

标题：Skill 脚本用相对层级常数推断跨目录根路径
来源：`docs/engineering/learning-extractor.md` 中三起已确认事件（`prepare_subtitles.py` 的 `parents[4]`、`prepare-youtube.mjs` 的 `../../../../..`、`film-style-replication/scripts/extract-mp4-frames.mjs` 的 `../../../../..`）
教训：skill 脚本要访问项目根、其他 skill 或运行时资产时，必须由真实存在的标记文件向上查找或由调用方显式传入，并支持环境变量覆盖；禁止用固定的 `../` 层数推断根目录。新增或改动后必须真实执行一次命令验证路径，发现定位失败要显式报错，不能继续执行到后续阶段的隐式错误。标记文件本身必须唯一：仓库里常有嵌套工作区（如 `apps/agents/`、`third-party/*`）携带同名标记，选标记前要先枚举全仓同名文件确认唯一，并核对解析结果确实等于期望根目录，不能只凭「命令没报错」或「向上找到了」就判定正确。

## HE-FL-002 把「未暴露 / 未接入」当成「能力不存在」直接回报缺口

标题：把「未暴露 / 未接入」当成「能力不存在」直接回报缺口
来源：`docs/engineering/learning-extractor.md` 中 `film_audio_gen` 事件（占位 `throw` 与 skill 文案互相印证，掩盖了早已存在的 `generateAudioToCanvas` 执行器）
教训：向用户报告「没有执行器 / 未接入 / 做不到」属于能力结论，必须先在运行时代码里核实证据：检索既有实现与真实调用点（谁在调用、输入输出契约是什么、是否已有等价工具或 API），确认不存在可复用实现后再报告。占位 `throw`、工具未暴露、skill 与文档表述都不构成事实证据；文档与运行时代码冲突时以代码为准，并在同一次改动里同步文档与 skill，避免错误结论继续被后续回合当作事实复用。

## HE-FL-003 用「看似等价」的数据源替代执行器真实数据源

标题：用「看似等价」的数据源替代执行器真实数据源
来源：`docs/engineering/learning-extractor.md` 中「video modelKey 契约不可满足」事件（首版目录工具接到只覆盖系统渠道的 new-api 运行时投影，实测 image/video/audio 三项全为 0）
教训：当契约要求「精确标识必须来自运行时目录」时，必须先确认该目录的数据源与执行器解析时使用的数据源是同一个，并用真实运行数据实测它在执行所在环境下非空；本地执行器目录与系统渠道运行时目录是两套来源，不能因为名称相近就互相替代。同时，若契约要求调用方提交「运行时目录返回的精确标识」，却没有任何工具或上下文能让调用方拿到该目录，这本身就是不可满足的契约，必须在实现侧补齐获取途径，而不是把失败归因于调用方填错。本类事件与 HE-FL-001（用固定层级常数推断根路径）同源：都是未用真实数据验证假设就推进实现。

## HE-FL-004 按提供方措辞做错误分类，漏掉经网关转发后改写的同义故障

标题：按提供方措辞做错误分类，漏掉经网关转发后改写的同义故障
来源：`docs/engineering/learning-extractor.md` 中两起已确认事件，同属 `apps/agents/packages/llm/llm-pi-ai/src/stream.ts` 的 `classifyPiAiError`：`2026-07-22` 的流截断分类缺陷，与本次 `session.v3.jsonl` 中 `Unexpected end of JSON input` / `Unterminated string in JSON` 被兜底成不可重试 `PI_AI_ERROR` 的复发
教训：凡按错误**文案**做分类、并据此决定「能否重试」的逻辑，必须把「同一物理故障经网关/代理/SDK 转发后措辞会变」当作已知前提，不能假定上游措辞稳定。分类应以可观测的结构事实为先，例如「帧是否完整」「是否缺少终止事件」，而不是依赖某个名词恰好出现在字符串里；同时必须为每一种新观察到的措辞补上回归用例。这类缺陷的代价不对称：漏判为可重试只是多试一次，漏判为不可重试会直接把一次网络抖动升级成整个回合的失败，并暴露给用户一个无从理解的报错。新增分类时还要显式区分「帧没收全」（可重试）与「帧收全但内容损坏」（不可重试），把边界写进测试而不是靠印象判断。

## HE-FL-005 外部书写规范放在 Agent 运行时读不到的 skill 根

标题：外部书写规范放在 Agent 运行时读不到的 skill 根
来源：`docs/engineering/learning-extractor.md` 中「H3 视频提示词未按官方格式生成」事件（MiniMax H3 官方规范只在 `.agents/skills/h3-prompt-writing/`，而原生 Agent 只挂载 `DSH_BUNDLED_SKILL_DIR=apps/agents/.agents/skills`）
教训：判断「某条规范是否对 Agent 生效」时，必须以运行时**真实挂载**的 skill 文本为准，不能因为仓库里存在同名规范文件就认定 Agent 已获得该内容。原生 preset 通过 `includeDefaultRoots: false` 关闭默认根、只挂载显式 bundled 根，因此开发侧 `.agents/skills/`、legacy `apps/agents-cli/skills/` 与运行时 `apps/agents/.agents/skills/` 是三份互不相干的副本，同一规范只写进其中一处就等于只在那一处生效。更糟的是这类缺失是静默的：后端契约若只校验字段名存在性（如 `validateH3PromptContract` 只查三个/六个段落名），不合规的产出仍能通过校验并被原样提交，偏差要到用户侧才暴露。新增或修改「生成模型必须遵守的外部书写规范」时，必须同步落到运行时 skill 根，并让结构校验覆盖规范中可机械判定的硬约束（首行对齐指令、时间戳格式、字段顺序），把「规范写了但没生效」从静默偏差变成显式失败。

## HE-FL-006 把「不需要消费产物」误读为「不需要产生产物」

标题：把「不需要消费产物」误读为「不需要产生产物」
来源：`docs/engineering/learning-extractor.md` 中 `youtube-storyboard` 默认抽帧被误删事件（用户说「逐张读图太慢」，我改成默认不抽代表帧、不拼 contact sheet，用户澄清后回滚）
教训：一个步骤的「产出」与「消费」是两件事，用户的抱怨往往只针对其中一件。用户说「某步骤太慢 / 不需要」时，必须先拆开问清是「不要生成这些文件」还是「生成但不去读它」，再决定改哪一段；砍掉消费通常只是改流程默认，砍掉产出则是删掉其他人可能依赖的资产，影响面完全不同。凡会改变默认产物集合的变更（让原本会生成的文件不再生成）应按高影响变更处理：先说明影响面与恢复方式，并检查是否有下游读者依赖该产物（本仓库中 `tapcanvas-film-style-replication/scripts/build-form-profile.mjs` 就读 `prepare-youtube.mjs` 的输出）。另外，反馈里的动宾结构要按字面拆解，不要自行替换成更宽的动词——「读图」是消费，「抽帧」是产出，二者不可互换。

## HE-FL-007 用经验常数与契约假设替代对真实产物的测量

标题：用经验常数与契约假设替代对真实产物的测量
来源：`docs/engineering/learning-extractor.md` 中 H3 音频「尾部大片静音 + 开头太急促」事件（时长预算统一套用中文语速 4.5 字/秒估英文、时间轴正则漏匹配 `At exactly`，交付滤镜无条件 `atrim=start=1` 砍掉真实人声）
教训：凡是「输出长度 / 时长 / 尺寸由经验常数推导」的逻辑，常数必须用真实产物或真实生成、按语种与场景分组校准，并把适用边界写进代码里；跨语言、跨单位（汉字 vs 拉丁字母）套用同一个常数属于未经测量的假设，会成倍放大偏差。同样，凡 prompt 契约里写了「模型应当遵守 X」（如「首秒无人声」），X 只是我们写下的要求，不是模型行为的证据——任何基于 X 的裁剪或校验，都必须先拿真实产物统计一次遵守率再决定；本仓库实测 23 条 H3 产物有 17 条不遵守该契约，固定裁剪等于从人声中间切一刀。修正时的取值要按代价不对称原则选边界：这里「估短 → 赶读/截断」的损失远大于「估长 → 留一点尾部静音」，故拉丁语速刻意取保守值。本类事件与 HE-FL-001、HE-FL-003 同源：都是未用真实数据验证假设就推进实现。

## HE-FL-008 只在仓内搜索就断言目标资产不存在，并给出无据的因果解释

标题：只在仓内搜索就断言目标资产不存在，并给出无据的因果解释
来源：`docs/engineering/learning-extractor.md` 中「错误经验登记 skill 缺失」事件（AI 声称 `.agents/skills/learning-extractor/SKILL.md` 不存在且「看起来是没拉取的 submodule」，实际该副本一直在上级工作区目录 `F:\aigc\aigc\.agents\skills\`，且仓库根本没有 `.gitmodules`）
教训：报告「某文件 / skill 不存在、未接入、未拉取」属于结论，必须先把搜索范围穷尽到仓库之外——同级与上级工作区目录、已知 skill 根、插件缓存——再下判断；只搜仓内就把「目标位置没有这个文件」升级成「该资产不存在」，会直接引出错误行动（本例是拒绝执行 AGENTS.md 要求的登记）。同时必须区分「目标位置的副本缺失」与「该资产整体不存在」，并禁止在未验证时给出带因果的解释（如「submodule 未拉取」）——这类解释听起来合理，却会让用户和后续会话把它当作已核实的事实继续复用，与 HE-FL-002 属同一类「把未验证的推断当事实上报」。给出结论前先自问：这个「不存在」是否只是「我没找到」。

## HE-FL-009 用静态输出键白名单与默认值替代上游真实输出契约

标题：用静态输出键白名单与默认值替代上游真实输出契约
来源：`docs/engineering/learning-extractor.md` 中「ComfyUI 工作流 emotion-basic 未产出媒体」事件（`audio_saved` 不在硬编码键白名单里，导致成功且已落盘的任务被判失败；`audio_info` 因缺 `type` 被 `|| "output"` 兜底成不可下载的假资产）
教训：从上游输出里挑选产物，判据必须来自产物自身的可观测结构，而不是节点名、键名或我们假设的命名规范。任何「按已知键名列表去取字段」的实现，都会随上游接入新节点而静默失效，并且失败方向极具误导性——它报的是「上游没产出」，而真相是「我们没看懂上游的产出」。同理，禁止对缺失字段填默认值来让流程继续（本例把无 `type` 的条目兜底成 `output`），那会把元数据伪造成可下载资产；应显式排除并保留其余真实产物。当出现「本地报错说上游没产出、上游却说自己成功」时，必须先去上游取回真实历史与产物并实测可下载性，再回头定位本侧判定条件；同时注意应用层 requestId 与上游 prompt_id 是两套 id，按 requestId 查上游历史只会得到空结果，必须按时间窗反查。修复这类提取逻辑时，要把它收敛成单一实现供同步与轮询两条路径共用，避免出现「轮询能取回、同步报未产出」的双轨行为。
## HE-FL-010 只按机器侧防覆盖设计产物布局，忽略人在真实文件系统里的可辨识性

标题：只按机器侧防覆盖设计产物布局，忽略人在真实文件系统里的可辨识性
来源：`docs/engineering/learning-extractor.md` 中 `youtube-storyboard` 本地视频产物平铺事件（产物直接写在视频所在目录，用户看到一堆 `scene-0.25-gap0.1-<指纹>` 与视频文件混放，反馈「现在太乱了」）
教训：脚本批量产出文件时，产物布局的首要约束是「用户能不能找到」，不是「程序会不会覆盖」。同一个输入产生的全部产物必须收进一个与输入同名的专属目录（本仓库约定为 `<输入文件名>.storyboard/`），让归属一眼可辨；哈希指纹这类机器标识只能用于目录内部的文件级防覆盖，不能当作人辨认归属的手段。审查这类能力时，要分别问三个消费者：程序自己（会不会混用旧结果）、下游脚本（能不能按路径找到事实文件）、用户本人（在资源管理器里能不能对上视频）；三者中任何一个被忽略都算布局缺陷。补充通用判据：产品自己内部的资源管理器视图也是「用户」，同理凡本地视频/素材相关 skill 与脚本，产物都应一个输入一个目录，不与原始素材平铺。

## HE-FL-011 把「可选的产出步骤」误当成「默认可省略的交付列」

标题：把「可选的产出步骤」误当成「默认可省略的交付列」
来源：`docs/engineering/learning-extractor.md` 中 `youtube-storyboard` 本地视频分镜事件（未传 `--subtitles` 导致「声音/对白」列 84 条全为 `unknown`，用户追问「音频文本怎么没输出了呀」；同轮还向用户复述了其从未提出的「画面描述」需求）
教训：skill 里写明「可以不传某参数 / 某步骤默认跳过」，说的是**执行成本可省**，不等于**交付表里对应的列可以不填**。判断某列是否属于本次交付，要看交付格式本身：像分镜表的「声音/对白」这类固定表头，只要源视频含对白就应默认具备字幕证据，整列 `unknown` 属缺项而非合规。执行前先把最终交付物（文件、表、字段）逐项列清，再决定哪些步骤可省；凡向用户复述其需求，必须先回读原始请求文本，不得凭印象或对「用户应该想要什么」的推断说出用户没提过的要求。同一范围内相邻的交付项（如切点与对白）要一起确认，不能因为砍掉某一个而顺手带走另一个。

现行护栏（强制前置检查）：执行 `youtube-storyboard` 前先按最终交付表逐列确认，凡「源视频含对白」的输入，必须显式传 `--subtitles whisper`（本地）或 `auto`（链接）并取得真实字幕证据后映射到每条镜头的 `dialogue`/`audio`；只有用户明确说“不要对白/只要时间码”，或源视频确认无人声（纯音乐、纯环境音），才允许记 `not_requested` 并让该列留空。交付前自检一遍分镜表：固定列不得整列 `unknown`，字幕来源/模型/片段数必须标注。该规则已写入 `SKILL.md`（frontmatter、硬边界 4、Workflow 第 3 步、Self-review、Delivery format、Anti-patterns）、`references/schema.md`、`agents/openai.yaml`，并由 `evals/evals.json` 的 id=9、id=10 做行为回归；漏传参数导致整列 `unknown` 一律判为缺项，必须补跑后再交付。

## HE-FL-012 把「子区间证据映射到父区间」简化成互斥择一归属

标题：把粒度差异带来的多条重叠当成冲突，用择一归属替代区间重叠判定
来源：`docs/engineering/learning-extractor.md` 中 `youtube-storyboard` 本地视频分镜事件（93 条镜头 vs 45 段 Whisper 字幕，第一版把每段字幕只归给重叠最长的镜头，导致 55/93 个镜头被误标 `dialogue: unknown`；实测 S002、S003 等镜头区间内确有人声）
教训：把细粒度证据映射到粗粒度区间（字幕→镜头、字符→段落、token→行、采样点→窗口）时，判据是「区间是否正重叠」，不是「取最大重叠或唯一归属」。粒度相差越大，一条细粒度证据与多个粗粒度区间重叠就越正常，这不是需要消歧的冲突；用择一归属会直接丢掉父区间的真实证据，并把「有数据」写成 `unknown`，而 `unknown` 在交付契约里恰恰表示「确无该证据」。只有当上游契约明确要求「一条证据只能被消费一次」时才允许择一，并且必须在交付物里写明该取舍及其影响范围。执行这条映射前先做一次覆盖自检：每条证据至少命中一个区间、每个区间都能由命中它的证据解释、总数与上游计数一致。

## HE-FL-013 把「上游 JSON 应该有某字段」当成已核实事实，未校验就写进交付物

标题：写入 provenance 字段前未校验字段存在，缺字段时写 undefined 而非显式失败
来源：`docs/engineering/learning-extractor.md` 中同一事件的次生错误（桥接层在字幕复用分支不带 `segmentCount`、场景复用分支不带 `sceneThreshold`，照读导致交付物出现「scene 阈值 undefined」「片段 undefined 段」等自相矛盾表述）
教训：往交付物写入来源、参数、计数这类 provenance 字段时，必须以「产出该事实的权威文件」为唯一依据，并在读取时校验字段存在、类型正确、与其它计数自洽（如 `segmentCount` 必须等于 `segments.length`）；任一不满足就显式失败。上游对象在复用、缓存、降级分支上少带字段是必须核对的运行时事实，不能默认为真；按本仓库「显式失败、零隐式回退」原则，缺字段既不允许写 `undefined`，也不允许用默认值补齐后继续。交付前必须把生成结果（尤其 Markdown 正文）读回来自检一遍，`undefined`/`NaN`/空 provenance 出现在成品里即判为未完成。本类事件与 HE-FL-002 同源：都是用未验证的推断替代对真实数据的核对。

## HE-FL-014 跨链路串用契约：把某条引擎的字段约束当成整个流程的通用规则

标题：跨链路串用契约：把某条引擎的字段约束当成整个流程的通用规则
来源：`docs/engineering/learning-extractor.md` 中 AI 生成角色双主角频道的音色一致性事件（把豆包 seed-audio TTS 的「参考图与参考音频互斥」说成通用规则，建议 H3 视频只连角色图、不传音色参考音频，用户反问「H3 生成视频的时候不是可以同时传音频和参考图吗」）
教训：本仓库同一能力域常有多条并存链路，各自输入契约不同——音频侧有 MiniMax relay、豆包 seed-audio TTS、H3 本地音频，视频侧有各厂商模型与 Ref2VA 全参考模式，它们的参数名、互斥关系、优先级规则互不通用。回答契约问题前必须先 `rg` 定位**该链路自己**的实现与 skill，再引用其中的约束；引用时必须说明它属于哪条链路。尤其警惕同一文件内的多引擎分支（如 `audio-speech.ts` 同时含 MiniMax 与豆包两套逻辑），其中某引擎的注释只对该引擎成立，不得上升为通用规则；也不要因为一处写了「A 与 B 互斥」就默认别处同样互斥——H3 视频恰好反过来，参考图（`assetObjectContracts` / `referenceImageNodeIds`）与参考音色（`referenceAudioUrls` / `voiceBinding`）是同一 clip 上同时下发的。本类事件与 HE-FL-002、HE-FL-008 同源：都是用未验证的推断替代对真实契约的核对，只是这次的错法更隐蔽——不是「我没查」，而是「我查了另一条链路」。
